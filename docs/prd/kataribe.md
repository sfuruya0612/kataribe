# Kataribe（会議録音・文字起こし・要約アプリ）PRD

Oct 26, 2026 · @Shoichi

## 概要

Kataribe は、Mac 上で会議音声を録音して mp3 として保存し、端末内で文字起こしを行い、その結果を任意の LLM（ChatGPT、Claude、Gemini など）に渡して会議のまとめと ToDo を Markdown で生成する Electron 製デスクトップアプリ。会議の備忘録を「録音ボタンを押す」以外の手間なく残すことを目的とする。

コアバリューは次の 3 点。

- 会議終了後、数分以内に「音声 mp3・文字起こし・要約・ToDo」が 1 フォルダにまとまって手元に残る
- 音声と文字起こしは既定で端末の外に出ない。LLM に送るのは文字起こし結果の Markdown のみで、ユーザーが明示的に操作したときに限る。OpenAI の文字起こし API を選んだ場合だけ、毎回の確認後に音声を送る
- 成果物はすべてプレーンな Markdown とファイルなので、Obsidian や Git など既存のメモ環境にそのまま取り込める

## プロジェクト名と根拠

プロジェクト名は **Kataribe（語り部）** とする。命名規則は既存ツール（AWS リソースを取ってくるツール = thief）に揃え、ファンタジー RPG のジョブ・役柄の名前で「そのツールがやる動作」を表す。

Kataribe を選んだ根拠は次の 3 点。

1. **役割が全工程と一致する。** 語り部は、その場で聞いた出来事を記憶し、後の人に語り継ぐ役。録音（聞く）・文字起こし（記憶する）・要約と ToDo（語り継ぐ）の 3 工程をそのまま表す。JRPG では村の歴史を語る NPC として定番で、ジョブ名で揃える命名規則に収まる
2. **検索で埋もれない。** 英語圏の一般語ではなく、ローマ字 1 語で検索を絞り込める。Scribe・Chronicler・Bard・Oracle のように同種ツールや大手サービスと同名になる問題がない。ただしアクセスログ解析ツール `kataribe`（Go 製）とオーディオブック生成アプリ「Kataribe: Audiobook.AI」が同名のため、GitHub のリポジトリ名もアプリ名と同じ `kataribe` とし、配布時は「Kataribe 会議録」と併記して用途を明示する
3. **主ユーザーに意味が直接伝わる。** 主ユーザーは日本語話者で、「語り部」は説明なしに役割が分かる。`kataribe` は打ちやすく、`Kataribe.app`・`~/Documents/Kataribe/` のいずれも収まりが良い

## 背景と課題

会議中にメモを取ると議論への参加が疎かになり、取らないと決定事項と宿題が数日で曖昧になる。Zoom や Google Meet の標準の文字起こし・要約機能は便利だが、対面会議では使えず、音声データが外部サービスに保存され、出力形式もサービスごとに閉じている。

既存の選択肢と Kataribe の立ち位置。

| 選択肢 | 対面会議 | オンライン会議 | 音声の保存先 | 出力 | 課題 |
| --- | --- | --- | --- | --- | --- |
| Zoom / Meet 標準機能 | 不可 | 可 | 各サービスのクラウド | サービス内 UI | 対面不可。データが外に出る。形式が閉じている |
| Otter / Notta 等の SaaS | 可 | 可 | ベンダーのクラウド | Web UI、エクスポート | 月額課金。社外秘の会議を預けにくい |
| macOS ボイスメモ + 手作業 | 可 | 不可 | 端末内 | 音声のみ | 文字起こし・要約が手作業 |
| Kataribe | 可 | 可 | 端末内 | mp3 + Markdown | 本 PRD の対象 |

Kataribe は「音声は既定で端末内、文字起こしはオフライン、LLM には文字起こし結果だけを明示操作で送る」という方針で、社外秘の会議でも使える備忘録ツールを目指す。OpenAI の文字起こし API は、利用者が明示的に選んだ場合だけ使う。

## ターゲットユーザーとユースケース

主ユーザーは、対面とオンラインの会議が混在するソフトウェアエンジニア・開発チームのリード。自分用の備忘録として使い、必要に応じて要約をチームに共有する。

| # | ユースケース | 入力 | 期待する結果 |
| --- | --- | --- | --- |
| U1 | 対面の定例会議（30〜60 分）を記録する | マイク音声 | 会議後に mp3・文字起こし・要約・ToDo がフォルダに保存される |
| U2 | Zoom / Meet の打ち合わせを記録する | システム音声 + マイク | 相手の声と自分の声の両方が 1 本の mp3 に入る |
| U3 | 1 on 1 の内容を自分だけの記録として残す | マイク音声 | 文字起こし・要約がローカルに残り、共有しない限り外に出ない |
| U4 | 過去の会議で「あの件はどう決まったか」を探す | キーワード | 文字起こし・要約を横断検索し、該当箇所の音声位置に飛べる |
| U5 | 要約を Slack や Notion に貼って共有する | 生成済み要約 | Markdown をコピーしてそのまま貼れる |
| U6 | 複数の会議にまたがる宿題を確認する | ToDo 一覧 | 未完了の ToDo を会議横断で確認し、完了を記録できる |

MVP では U1〜U3、U5、U6 を満たす。U4 は検索機能として次フェーズで扱う。

## スコープ

MVP は「録音 → mp3 保存 → 文字起こし → LLM 要約・ToDo → Markdown 保存」の一本の流れを、1 人のユーザーが毎日使える品質で完成させる。

**MVP に含む**

- マイク録音とシステム音声録音の切り替え（併用も可）
- BlackHole 2ch のセットアップガイドと入力デバイスの検出
- mp3 への書き出しと、文字起こし用 wav の自動生成
- whisper.cpp によるオフライン文字起こし（日本語・英語）
- OpenAI の文字起こし API を任意で選べる文字起こしエンジン
- RE-USE の音声強調を WebGPU で実行し、録音停止後と文字起こし前の 2 点で ON/OFF できる任意機能。アプリは商用利用が可能なモデルだけを使う
- 要約の前に相槌と擬音を除く任意の前処理
- 話者分離（2〜10 人）
- 話者分離結果の再利用と話者名の保持
- 任意の LLM プロバイダ（OpenAI 互換 API）への文字起こし送信と、要約・決定事項・ToDo の Markdown 生成
- 会議ごとのフォルダ保存と、アプリ内の会議一覧
- 要約の ToDo を全会議横断で確認し、完了状態を保存できる一覧
- UI の表示言語（日本語・英語）の切り替え

**次フェーズ**

- 文字起こし・要約の全文検索と、該当箇所の音声再生
- 要約テンプレートのカスタマイズ（1 on 1 用、ふりかえり用など）
- mp3 を直接 Gemini に渡す音声入力モード

**対象外**

- Windows / Linux 対応
- macOS 14.1 以前
- Intel Mac
- 複数ユーザーでの共有・同期機能
- Slack / Notion / カレンダーへの自動投稿（Herald として別モジュール化を検討）
- リアルタイム字幕表示
- 送信前の個人名・社名のマスク。送信先が入力を学習に使うか、送信すること自体のリスクは、プロバイダを選ぶユーザーの判断に任せる

## 機能要件

優先度は Must = MVP 必須、Should = MVP で入れたいが落とせる、Could = 次フェーズ。

**録音**

| ID | 要件 | 優先度 |
| --- | --- | --- |
| R-1 | メニューバーまたはメインウィンドウから 1 クリックで録音を開始・停止できる | Must |
| R-2 | 入力ソースを「マイク」「システム音声（BlackHole 2ch）」「両方」から選べ、録音中も現在の設定が見える | Must |
| R-3 | 録音中は経過時間と入力レベルを表示し、無音が続く場合は警告する | Should |
| R-4 | 停止時に mp3（64 kbps・モノラル。設定で 128 kbps に変更可）と文字起こし用 wav（16 kHz・mono）を保存する。wav は Application Support の一時ディレクトリに置き、文字起こし完了後に削除し、再文字起こし時は mp3 から再生成する | Must |
| R-5 | アプリやマシンが落ちた場合も、直前までの音声が復旧できる（チャンク単位で逐次保存） | Should |

**文字起こし**

| ID | 要件 | 優先度 |
| --- | --- | --- |
| T-1 | 録音停止後、自動で whisper.cpp による文字起こしを開始する | Must |
| T-2 | モデル（small / medium / large-v3-turbo 等）を設定画面で選び、アプリ内からダウンロードできる | Must |
| T-3 | 文字起こし結果をタイムスタンプ付き Markdown として保存する | Must |
| T-4 | 進捗（最後のセグメント終了時刻 ÷ 音声長）と予想残り時間を表示し、キャンセルできる | Should |
| T-5 | 文字起こし結果をアプリ内で編集し、修正を保存できる | Should |
| T-6 | 既存の mp3 / wav ファイルを取り込んで文字起こしできる | Could |
| T-7 | 多言語が混在する音声に対応する。言語は自動判定（既定のヒントは日本語）し、文字起こしは話された言語のまま残す。文字起こしの日本語訳・英語訳は LLM によるオプションとして提供する | Must |
| T-8 | 文字起こしの完了は「プロセスが終了コード 0 で終了」「最後のセグメントの終了時刻が音声長 − 15 秒以上」「出力が空でない」の 3 条件で判定する。1 つでも欠ければエラーとして扱う | Must |
| T-9 | タイムアウトは固定秒数ではなく進捗で判定する。最後のセグメントが出てから 3 分（large 系モデルは 5 分）新しいセグメントが出なければ停止とみなす。保険として「予想時間 × 3、最低 5 分」のハードリミットを置く。予想時間 = 音声長 × 実測の処理速度比（初回に計測して保存。初期値は Apple Silicon で 0.2）。Mac のスリープ中は計時を止める | Must |
| T-10 | タイムアウト時は、それまでのセグメントを部分文字起こしとして保存したうえでプロセスを終了し、最後のセグメント終了時刻から 1 回だけ自動で再開する（--offset-t）。それでも失敗したら、1 段小さいモデルでの再実行を提案する | Should |

T-7 の多言語混在の完全対応は、whisper.cpp のファイル単位の言語判定の制約があり、リスクと未決事項に記載する。

**REQ-TRANS-001 文字起こしエンジンの選択**
優先度: Must
利用者は、文字起こしを端末内の whisper.cpp で行うか、OpenAI の文字起こし API で行うかを選べる。既定のエンジンは whisper.cpp とし、OpenAI のモデルも既定は `whisper-1` とする。

受入基準:
- 設定画面の「文字起こし」で、文字起こしエンジンを「ローカル (whisper.cpp)」と「OpenAI API」から選べる。
- 既定のエンジンはローカル (whisper.cpp) とする。
- OpenAI API を選んだとき、音声を送信する前に、送信先のホスト、モデル、音声の長さ、分割数、音声が端末外に出ることを確認ダイアログに表示する。
- 確認ダイアログで送信を承認したときだけ、音声を OpenAI API に送る。
- 承認しなかったときは音声を送らず、ローカルの whisper.cpp で文字起こしを続ける。ローカルのモデルがない場合は、モデルがない旨を表示する。
- OpenAI API の文字起こしモデルとして `whisper-1`、`gpt-4o-transcribe`、`gpt-4o-mini-transcribe` を選べる。既定は `whisper-1` とする。
- `whisper-1` 以外のモデルを選んだとき、文字起こしのタイムスタンプが分割単位になることを設定画面に表示する。
- OpenAI API の API キーは、Provider が ChatGPT の LLM プロファイルに保存したキーを使う。文字起こし専用のキーを別に保存しない。
- OpenAI API のリクエストは API の上限以下に分割し、分割した各区間の開始時刻を加算して文字起こしの時刻にする。
- OpenAI API が失敗したときは、成功した区間までの文字起こしを部分結果として保存し、失敗の理由を会議詳細に表示する。
- OpenAI API に送るのは文字起こし用の音声と、モデル名、用語集、応答形式だけとし、会議のタイトル、日付、保存先のパスは送らない。

**REQ-ENHANCE-001 録音停止後の保存音声の強調**
優先度: Should
利用者は、録音停止後と会議詳細から、保存する音声へ RE-USE の音声強調を適用するかどうかを選べる。生の音声を残し、強調した音声と聞き比べられる。

受入基準:
- 設定画面の「文字起こし」で、録音停止後の保存音声の強調を ON/OFF できる。既定は OFF とする。
- 強調には、商用利用が可能な `nvidia/NVIDIA-NemotronLabs-RE-USE` を使う。アプリは研究および教育用のモデルを選択肢に含めない。
- モデルは初回利用時にダウンロードし、SHA-256 を照合してから使う。進捗、キャンセル、削除ができる。
- 強調は端末内の WebGPU で行い、音声を外部に送らない。
- 強調を ON にした会議は、生の `audio.mp3` を残し、`audio.enhanced.nemotronlabs.mp3` を保存する。
- 会議詳細から、インストール済みの商用モデルで保存音声の強調を再実行できる。再実行の入力は保存済みの `audio.mp3` から作る。録音した会議では、録音直後の強調と入力が異なることを表示する。
- 再実行に成功したときは以前の強調音声を新しい結果で置き換え、失敗したときは以前の強調音声を残す。
- 会議詳細の音声プレイヤーで、生音声と強調音声を切り替えて再生できる。
- 強調に失敗したときは生の `audio.mp3` を残し、失敗理由を会議詳細に表示する。文字起こしと要約は続行する。
- 強調の処理時間、使用モデル、設定、入出力のハッシュを `enhancement.json` に記録する。
- `audio.mp3` のハッシュが変わったときは、古い強調音声を削除する。

**REQ-ENHANCE-002 文字起こし前の強調と比較**
優先度: Should
利用者は、文字起こしの前に RE-USE の音声強調を適用するかどうかを選べる。生の文字起こしと、強調した文字起こしを保存し、会議詳細で切り替えて比較できる。
比較セッションは、1 つの 16 kHz WAV から生と強調の文字起こしを作る単位とする。

受入基準:
- 設定画面の「文字起こし」で、文字起こし前の強調を ON/OFF できる。既定は OFF とする。
- 強調を ON にした会議は、比較セッションで `audio.mp3` から 16 kHz WAV を 1 回だけ作り、生の文字起こしと強調の入力の共通の親にする。強調した 16 kHz WAV はその WAV から作る。比較セッションでは PCM 由来の `audio.16k.wav` を作らない。
- 比較用に、生の音声で文字起こしした `transcript.raw.md` と、強調した音声で文字起こしした `transcript.nemotronlabs.md` を保存する。`transcript.md` は強調した結果を正とし、強調に失敗したときは生の結果を正とする。
- 会議詳細の文字起こしペインで、生と強調の文字起こしを切り替えて比較できる。比較用の文字起こしは読み取り専用のスナップショットとし、本文は生成時の内容を保持する。front matter の title は会議タイトルに追従する。
- 会議詳細から、インストール済みの商用モデルで文字起こし前の強調を再実行できる。再実行の前に既存の `transcript.md` を `transcript.previous.md` にコピーし、上書きを確認する。コピー後も `transcript.md` は成功するまで変更しない。
- 再実行は、生と強調の両方の文字起こしが成功したときだけ成功とする。成功したときは比較用の文字起こしと `transcript.md` を新しい結果で置き換え、どちらかが失敗またはキャンセルしたときは以前の結果を残す。
- 文字起こしの再実行に成功したときは、既存の要約と翻訳が以前の文字起こしに基づくことを会議詳細に表示する。
- 初回の文字起こしで強調に失敗したときは、生の音声で文字起こしし、失敗理由を会議詳細に表示する。比較用は成功した側だけを保存する。
- OpenAI の文字起こし API を選んだときは、音声の二重送信を避けるため、生との比較を行わない。文字起こし前の強調が ON なら強調した音声だけを 1 回送り、OFF なら生の音声だけを 1 回送る。強調に失敗したときは生の音声を送る。送信の確認ダイアログには、強調の設定と成否に応じて送る音声を表示する。
- 要約と翻訳は `transcript.md` を使い、ToDo は `summary.md` を使う。`transcript.raw.md` と `transcript.nemotronlabs.md` は比較用であり、要約、翻訳、検索、ToDo の入力にしない。
- 強調と文字起こしの処理時間、使用モデル、設定、入出力のハッシュを `enhancement.json` に記録する。
- `audio.mp3` のハッシュが変わったとき、文字起こし前の強調を OFF にして再文字起こししたとき、OpenAI の文字起こし API を選んだとき、比較セッションの入力が変わったとき、モデルの重みの SHA-256 が変わったときは、古い比較用の文字起こしを削除する。

**話者分離**

**REQ-DIAR-001 複数話者の分離**
優先度: Must
話者分離を有効にすると、文字起こしの各発話に話者ラベルを付ける。

受入基準:
- 2 人以上の話者が検出された場合、最初に現れた順に `話者A` から `話者J` のラベルが付く。
- 話者数は自動検出を既定とし、2〜10 人を指定できる。
- 自動検出が 10 人を超えた場合、10 人にまとめる。
- 話者名を会議ごとに変更でき、文字起こしと、話者名を保持している既存の翻訳の話者ラベルに反映される。
- 話者分離に失敗しても文字起こしは保存され、失敗理由が会議詳細に表示される。
- 話者分離モデルは初回利用時にダウンロードされ、SHA-256 を照合してから使われる。

**REQ-DIAR-002 話者分離結果の再利用と話者名の保持**
優先度: Should
同じ音声と同じ話者分離設定で再文字起こしするとき、保存済みの話者ターンを再利用し、クラスタ ID に付けた話者名を保持する。
ここでの同じ音声は、会議の `audio.mp3` の SHA-256 が同じことを指す。
この要求は `raw` の入力に適用する。強調の有無、強調モデル、強調設定の変更は REQ-DIAR-003 に従う。

受入基準:
- 同じ音声と同じ話者分離設定で再文字起こししたとき、話者分離の CLI を起動せず、保存済みターンでラベルを付ける。
- クラスタ ID に付けた話者名が、再文字起こし後の文字起こしと、話者名を保持している翻訳に残る。
- 音声、話者セグメンテーションモデル、話者埋め込みモデル、話者数、クラスタ閾値のいずれかが変わったとき、キャッシュを無効化して話者分離を再実行する。
- キャッシュの読み書きに失敗しても、文字起こしと話者分離は完了する。

## アーキテクチャと技術選定

Electron は UI とジョブ管理に専念し、録音は Renderer の Web Audio で行い、エンコードと文字起こしは子プロセスに切り出す。文字起こし中も UI が固まらず、アプリ独自のネイティブコードを持たない。既製のネイティブモジュールと同梱バイナリは例外とする。

&#91;embedded content: Kataribe のアーキテクチャ（Electron 2 層 + 子プロセス 4 つ）\]

Renderer が書き出す wav チャンクを ffmpeg が mp3 に変換し、文字起こし前の強調が OFF のときは文字起こし用 wav も作る。ON のときは `audio.mp3` から作った 16 kHz WAV から生と強調の比較用文字起こしを保存する。whisper.cpp が transcript.md を作る。音声強調はアプリ内の WebGPU ワーカーで実行し、音声は端末外に出さない。LLM クライアントだけがネットワークに出る。

| 層 | 技術 | 選定理由 |
| --- | --- | --- |
| アプリ基盤 | Electron + TypeScript + React + Vite | 要望通り Electron。Vite で開発時の起動を速くする |
| マイク録音 | Renderer の getUserMedia + Web Audio（AudioWorklet） | Electron 標準機能で済み、ネイティブコードが不要。入力デバイスの選択は enumerateDevices で行う |
| システム音声 | BlackHole 2ch などの仮想オーディオデバイスを入力デバイスとして使う | 画面収録権限が不要で、署名なしでも取得できる。利用者に BlackHole 2ch のインストールと Multi-Output Device の設定が必要 |
| エンコード | ffmpeg（同梱バイナリ） | mp3（libmp3lame）と 16 kHz wav の両方を 1 ツールで出せる |
| 音声強調 | アプリ内の WebGPU ワーカーで RE-USE を実行し、モデルの重みは初回にダウンロードする | 音声を外部に送らず、PyTorch を同梱せずにモデルを差し替えられる。WebGPU の対応と GPU メモリに依存する |
| 文字起こし | 既定は whisper.cpp（Metal / Core ML ビルド）を子プロセスで実行し、任意で OpenAI の文字起こし API を使う | オフライン要件を既定で満たす。Apple Silicon で実用速度が出る。OpenAI API は音声を送る代わりに、モデルと端末の負荷を選ばずに高い精度を狙える |
| LLM | OpenAI 互換 Chat Completions を共通インターフェースにし、プロバイダ別のアダプタで差分を吸収 | OpenAI・Gemini・Ollama Cloud・Fireworks AI は OpenAI 互換エンドポイントを提供しており 1 実装で済む。Anthropic は差分のある部分だけ専用アダプタ。GitHub Models は 2026-07-30 に廃止されたため、6 つ目のプリセットは未定 |
| シークレット | Electron の safeStorage（macOS Keychain 裏付け） | 追加のネイティブモジュールなしで Keychain に保存できる |
| メタデータ・検索 | 会議ごとの meta.json + SQLite（better-sqlite3）。索引は Application Support に置き、FTS5 は次フェーズ | ファイルが正で SQLite は再構築可能な索引。フォルダをコピーすれば移行できる |
| 配布 | electron-builder（dmg、署名・公証） | Gatekeeper 警告を出さないために必須 |

## ユーザーフローと画面構成

基本フローは「録音開始 → 停止 → 自動で文字起こし → 要約ボタン → 保存」の 5 ステップで、ユーザーが操作するのは録音の開始・停止と要約の実行の 3 回だけ。

1. メニューバーのアイコンまたはメインウィンドウで入力ソース（マイク / システム音声 / 両方）を選び、録音を開始する。初回のみマイク権限のダイアログが出る。システム音声を使う場合は、事前に BlackHole 2ch と Multi-Output Device を設定する
2. 録音中は経過時間と入力レベルが表示される。会議フォルダと一時ディレクトリはこの時点で作られ、10 秒ごとに wav チャンクが書き込まれる
3. 停止すると ffmpeg が mp3 を生成し、文字起こし前の強調が OFF のときは PCM から 16 kHz wav も生成する。ON のときは比較セッションで `audio.mp3` から 16 kHz WAV を作り、その WAV から生と強調の文字起こしを作る。保存音声の強調と文字起こし前の強調は独立して設定する。既定は whisper.cpp で、OpenAI API を選んだ場合は音声を送る前に確認ダイアログが出る。進捗は会議一覧の該当行に出る
4. 文字起こしが終わると会議詳細画面が開く。音声と文字起こしは、生と強調結果を切り替えて比較できる。音声と文字起こしの強調は、会議詳細からインストール済みの商用モデルで再実行できる。話者名を確認して変更し、文字起こしを確認して修正し、「要約を生成」を押す。送信前に送る内容と送信先 (選択中のプロバイダとモデル) を確認するダイアログが出る。相槌と擬音を除く設定が有効なときは、同じ確認ダイアログに 2 回送信する旨を表示する
5. 要約・決定事項・ToDo・未決事項が summary.md として保存され、詳細画面に表示される。コピーボタンで Markdown をクリップボードに取り出せる。ToDo は全会議横断の一覧からも確認でき、チェックを切り替えると要約のチェックボックスに保存される

画面は 5 つに絞る。

| 画面 | 役割 | 主な要素 |
| --- | --- | --- |
| メニューバー | 常駐。録音の開始・停止だけを素早く行う | 録音ボタン、入力ソース切り替え、経過時間、メインウィンドウを開く |
| 会議一覧 | 過去の会議を探し、処理状況を見る | 日付、タイトル、長さ、状態 (録音中 / 音声強調中 / 文字起こし中 / 要約済み) の一覧、タイトル編集 |
| 会議詳細 | 1 つの会議の成果物を見て編集する | 音声プレイヤー (生 / 強調)、文字起こし (タイムスタンプ付き、現在の文字起こしは編集可、生 / 強調は読み取り専用)、音声と文字起こしの強調の再実行、音声強調の状態、処理時間、使用モデル、話者名の変更、要約タブ、要約生成ボタン、コピー |
| ToDo 一覧 | 全会議の ToDo を確認し、完了状態を記録する | 未完了 / 完了 / すべての切り替え、会議名と日付付きの ToDo、チェックボックス、会議詳細への移動 |

## データ・ファイル設計

会議 1 件 = フォルダ 1 つ。アプリを消してもフォルダだけで内容がすべて読める構成にする。フォルダ名は「YYYY-MM-DD\_タイトル」とし、タイトル未入力時は「タイトル未入力」を入れる（例: 2026-10-26\_タイトル未入力）。後からタイトルを付けるとフォルダ名も改名する。同じ日付とタイトルの会議が複数ある場合は、末尾に連番を付ける。
タイトルが未入力の場合は要約生成時に LLM でタイトルを付け、失敗した場合は理由と再試行を会議詳細に表示する。

最終成果物は保存先ルートに置き、録音中の一時ファイルと検索の索引は Application Support に置く。保存先がクラウド同期の対象でも、録音中の音声と索引を同期させないためである。

```
~/Documents/Kataribe/
├── 2026/
│   └── 2026-10-26_週次定例/
│       ├── audio.mp3          # 64 kbps モノラル。保存用 (設定で 128 kbps)
│       ├── audio.enhanced.nemotronlabs.mp3 # 商用利用が可能なモデルで強調した保存用
│       ├── transcript.md      # タイムスタンプ付き文字起こし。強調の結果。失敗時は生の結果
│       ├── transcript.previous.md # 文字起こし前の強調の再実行前のコピー
│       ├── transcript.raw.md  # 強調前の比較用。読み取り専用
│       ├── transcript.nemotronlabs.md # 強調した比較用。読み取り専用
│       ├── enhancement.json   # 音声強調の状態の正本
│       ├── diarization.json   # 話者ターンと話者名のキャッシュ
│       ├── summary.md         # LLM が生成した要約・ToDo
│       └── meta.json          # 録音条件・処理状況・使用モデル

~/Library/Application Support/Kataribe/
├── tmp/<meeting-id>/
│   ├── chunks/                # 録音中の一時 wav。停止後に結合して削除
│   ├── audio.16k.wav          # 16 kHz モノラル。文字起こし用。完了後に削除
│   ├── audio.16k.enhanced.wav # 強調した 16 kHz モノラル。文字起こし用。完了後に削除
│   └── audio.decoded.wav      # mp3 からデコードした強調の入力。完了後に削除
├── index/<保存先ルートのハッシュ>.sqlite  # 一覧・検索用。フォルダから再構築可能
└── models/                    # whisper.cpp、話者分離、RE-USE のモデル
    ├── whisper/               # whisper.cpp のモデル。初回利用時にダウンロード
    ├── diarization/           # 話者分離モデル。初回利用時にダウンロード
    └── reuse/                 # RE-USE の重み。商用利用が可能なモデルだけを置く
        └── nemotronlabs.safetensors
```

`audio.wav` は処理中だけ会議フォルダに置き、保存音声の強調と、OFF のときの 16 kHz WAV の生成後に削除する。保存先がクラウド同期の対象の場合、処理中は `audio.wav` も同期され得る。
`audio.16k.wav` は、通常の文字起こしでは PCM から作り、文字起こし前の強調を ON にした比較セッションでは `audio.mp3` から作る。

音声強調の比較ファイルは検証用の派生物であり、`audio.mp3` と `transcript.md` を正とする。`transcript.raw.md` と `transcript.nemotronlabs.md` は要約、翻訳、検索、ToDo の入力にしない。要約は `transcript.md`、ToDo は `summary.md` を使う。

transcript.md の形式。見出しに会議情報、本文は「開始秒 → テキスト」の行で、検索結果から音声位置に飛ぶために秒数を残す。

```markdown
---
title: 週次定例
date: 2026-10-26T14:00:00+09:00
duration: 00:52:13
source: mic+system
model: ggml-large-v3-turbo
---

[00:00:04] 話者A: 今日は先週のリリース後の障害対応と、来期の計画について話します。
[00:00:21] 話者B: 障害の原因はキャッシュの設定ミスで、金曜に修正済みです。
```

summary.md は固定の 4 セクションを持ち、ToDo はチェックボックス付きの行にして Obsidian 等でそのままタスクとして扱えるようにする。
ToDo の完了状態は summary.md のチェックボックスに保存する。ToDo 一覧は各会議の summary.md を読み、チェックボックスの状態をそのまま表示する。

```markdown
---
title: 週次定例
date: 2026-10-26
provider: claude
generated_at: 2026-10-26T15:05:12+09:00
---

## 要約

## 決定事項

## ToDo

- [ ] キャッシュ設定の再発防止策をまとめる（担当: 田中、期限: 10/30）

## 未決事項
```

meta.json は処理の再開と再実行に使う。`status` は recording / encoding / enhancing / transcribing / transcribed / summarized / error のいずれかで、各段階の開始と終了の時刻、使ったモデルとプロバイダを持つ。
音声強調の詳細は `enhancement.json` を正とし、`meta.json` の `enhancement` には、強調音声があるモデル、直近の保存音声の状態、生の比較用文字起こしの有無、比較用文字起こしがあるモデル、正にした文字起こしの種類だけを持つ。
検索索引の会議の行には、強調音声があるモデル、生の比較用文字起こしの有無、比較用文字起こしがあるモデル、直近の音声強調の状態を持つ。

## 成功指標

MVP は「自分の会議で 4 週間、毎回使い続けられるか」で判断する。数値はすべて作者自身の利用で測る。

| 指標 | 目標 | 測り方 |
| --- | --- | --- |
| 録音の取りこぼし | 4 週間で 0 件 | 会議後に mp3 の長さと実際の会議時間を照合する |
| システム音声の欠落 | 4 週間で 0 件 | meta.json の無音警告、復旧時刻、BlackHole の非ゼロ割合を確認する |
| 文字起こし所要時間 | 音声強調を OFF にした既定経路で、会議時間の 1/6 以下 (60 分なら 10 分以内) | meta.json の transcribing 開始と終了の時刻 |
| 文字起こしの修正量 | 要約前に直す箇所が 1 会議あたり 10 箇所以下 | 編集前後の diff 行数 |
| 要約の採用率 | 生成した ToDo のうち、そのまま使えるものが 8 割以上 | 手で削除・書き換えた ToDo の数 |
| 会議後の作業時間 | 音声強調を OFF にした既定経路で、録音停止から共有用の要約が手元にあるまで 15 分以内 | 停止時刻と summary.md の生成時刻 |
| 継続利用 | 4 週間、対象の会議すべてで使った | 会議一覧の件数とカレンダーの会議数の比較 |

## リスクと未決事項

最大のリスクはシステム音声のセットアップで、ここが MVP の利用者テストで崩れると構成全体が変わる。

| リスク | 影響 | 対策 |
| --- | --- | --- |
| BlackHole 2ch のインストールや Multi-Output Device の設定でつまずく | U2 のシステム音声が録れない | README の初回設定チェックリスト、入力デバイスの検出、短いテスト録音を用意する。設定画面には README へのリンクを置く |
| 録音中に音声出力が BlackHole から外れる | BlackHole 入力が無音になるが読み取りは続き、録音が成功したように見える | 直近のシステム音声レベルを監視し、無音が続いたら警告する |
| スピーカー再生中にマイクが相手の声を拾い、二重に録音される | 文字起こしが重複し、要約の品質が下がる | ヘッドホンを推奨し、録音開始前に注意を出す。エコーキャンセルは会議アプリの音声には効かない場合があるため、MVP の対策に含めない |
| Bluetooth ヘッドホンのマイクを入力に使うと HFP に切り替わり、出力品質が下がる | 利用者が聞く会議音声の品質が落ちる。自分の声も HFP の品質で録音される | 入力は内蔵マイクまたは USB マイク、出力は Bluetooth ヘッドホン（A2DP）を推奨する。macOS の既定入力と会議アプリのマイクも内蔵/USB にし、Bluetooth ヘッドホンを入力と出力の両方に使わないよう README で案内する |
| マイク入力が大きすぎてクリッピングする | 文字起こしの品質が下がる | 入力レベルにクリッピング警告を出し、ゲイン調整を案内する |
| 日本語の文字起こし精度が会議の専門用語で落ちる | 要約の質が下がり、修正量が増える | whisper.cpp の initial prompt に用語集を渡す設定を文字起こし機能と同時に入れる。修正しやすい編集 UI を優先する |
| 多言語が混在する会議で、whisper.cpp のファイル単位の言語判定が主言語に引っ張られる | T-7 の「話された言語のまま残す」を完全には満たせない | VAD で区間ごとに言語判定するか、T-7 を主言語の自動判定に限定するかを決める |
| 声質の近い参加者や重なり発話で話者ラベルが誤る | 文字起こしの可読性が下がり、要約の担当者推定も誤る | 話者名を会議ごとに変更できるようにする。話者ラベルが推定であることを設定画面と README に明記する |
| LLM API の料金・レート制限 | 長い会議で要約が失敗する、コストが読めない | 送信前に概算トークン数と料金を表示する。分割送信（S-6）で上限を回避する。相槌と擬音の除去を有効にすると送信回数が増えるため、確認ダイアログに表示する |
| OpenAI の文字起こし API に音声を送る | 音声が端末外に出る | 既定はローカルの whisper.cpp とし、OpenAI を選んだときだけ、送信のたびに音声が端末外に出ることを確認する。音声を送るのは文字起こしの実行時だけとする |
| 相槌と擬音の除去で本文が変わる | 話者の意図やニュアンスが失われる | 相槌と擬音だけを除くようプロンプトで指示し、話者ラベルとタイムスタンプを保持する。除去に失敗したときは元の文字起こしで要約する |
| 要約を再生成すると ToDo の完了状態が失われる | 完了済みのタスクが未完了に戻り、ToDo 一覧の信頼性が下がる | 送信前の確認ダイアログで、既存の要約を上書きすることと完了状態を引き継がないことを警告する。直前の要約は summary.previous.md に退避する |
| WebGPU が使えない、または GPU メモリが足りない | 音声強調を実行できない | 起動時と実行前に WebGPU の可用性を確認し、使えないときは機能を無効にして理由を表示する。CPU への暗黙のフォールバックをしない |
| 音声強調の処理が長い | 会議後に待ち時間が増える | 短いチャンクで逐次処理し、進捗とキャンセルを表示する。検証では短い会議から始める |
| アプリ内に同梱する WebGPU エンジンが非公式である | モデルや macOS の更新で壊れる可能性がある | エンジンを独立したモジュールに閉じ込め、入力と出力の契約をテストで固定する。公式の推論経路が提供されたら差し替える |
| 音声と文字起こしの生と強調を保存する | ディスク使用量が増える | 保存音声の強調を ON にした会議だけ `audio.enhanced.nemotronlabs.mp3`、文字起こし前の強調を ON にした会議だけ `transcript.raw.md` と `transcript.nemotronlabs.md` を保存する。どちらも OFF の会議は従来どおり 1 つの音声と 1 つの文字起こしにする |
| 音声強調の比較用文字起こしが要約や検索に混ざる | 会議の内容と異なる文字起こしが検索や要約に使われる | 要約と翻訳は `transcript.md`、ToDo は `summary.md` だけを使う。比較用は読み取り専用にし、検索索引に含めない |
| 音声強調の一時ファイルでディスクを圧迫する | 録音や他のアプリの保存が失敗する | 一時ファイルを Application Support の tmp に置き、成功、失敗、キャンセル、起動時に削除する。開始前に空き容量を確認する |
| 署名・公証の手順が未経験 | 配布が遅れる | Apple Developer Program の登録を早めに済ませ、CI で署名ビルドを回す |
| 録音中のアプリ更新・スリープ | 録音が途切れる | 録音中はスリープ抑止（powerSaveBlocker）を入れ、自動更新を保留する |

2026-10-28 から 10-29 の M0 では、desktopCapturer と ScreenCaptureKit は署名なしで音声を取得できなかった。
BlackHole 2ch 0.7.1 を入力デバイスとして使う経路は成功し、ピーク 0.14999、RMS 0.1061 を確認した。
Multi-Output Device 経由の取得と、マイク + BlackHole の同時ミックスも成功した。
AirPods 出力 + BlackHole の Multi-Output も成功した。
録音中に出力を BlackHole から外すと、BlackHole は無音のサンプルを返し続けたため、無音検出が必要である。
M0 のフレーム数は `AnalyserNode` の読み取り回数であり、実フレーム数ではない。
2026-10-29 に M0 ハーネスを実フレーム数のカウンタに更新した。
10 秒の予備測定では、BlackHole、マイク、ミックスの `frames` と `expectedFrames` が 479,744、`gaps` と `missedFrames` が 0 だった。
60 分の連続録音は実フレーム数で再測定し、BlackHole は 172,779,648 / 172,779,776 フレーム、マイクとミックスは 172,779,520 / 172,779,520 フレームだった。
BlackHole のカウンタで 128 フレームの gap が 1 回検出された。
ウォームアップ 1 秒を入れた 60 秒テストでは gaps 0 だったため、起動時の数え落としと確認した。
ウォームアップなしのディスプレイスリープでは 256 フレームの gap が 1 回出たが、ウォームアップ 1 秒を入れた再測定では gap 0 だった。
システムスリープでは 81.394 秒の欠落があった。
システムスリープの欠落は `power_suspend` と `power_resume` で記録する。
Zoom / Meet の 300 秒は、BlackHole、マイク、ミックスが 14,390,016 / 14,390,272 フレームで、ウォームアップなしでは 256 フレームの gap が 1 回だった。
ウォームアップ 1 秒を入れた 60 秒テストでは gap 0 だったため、起動時の数え落としと確認した。
詳細は ADR-0003。

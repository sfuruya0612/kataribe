# RE-USE の文字起こし精度に対する検証

OpenAI の文字起こし API と相槌の除去を追加する前に、NVIDIA の音声強調モデル RE-USE を文字起こしの前処理に使う価値があるかを検証した。
この文書は、検証の条件、結果、判断の根拠を残す。
判断そのものは ADR-0026 が持つ。

## 検証したモデル

NVIDIA は RE-USE の名前で 2 つのモデルを公開している。

| モデル | ライセンス | 位置付け |
| --- | --- | --- |
| `nvidia/NVIDIA-NemotronLabs-RE-USE` | OpenMDW-1.1 | 商用利用が可能な公開モデル。9.6M パラメータ |
| `nvidia/RE-USE` | NVIDIA One-Way Noncommercial License (NSCLv1) | 研究開発用の先行モデル。商用利用は不可 |

Kataribe を配布する場合に使えるのは、商用利用が可能な `NVIDIA-NemotronLabs-RE-USE` である。
検証には `NVIDIA-NemotronLabs-RE-USE` を使った。

公式の推論は Linux と NVIDIA Ampere の GPU を前提とする。
macOS で動かすため、非公式の macOS 移植 [`yani-/re-use-mac-unofficial`](https://github.com/yani-/re-use-mac-unofficial) を commit `6d794f84097896ea0fcb36523e2fb998e23ec68d` で使った。
この移植は Mamba 層を PyTorch と Metal のカーネルで置き換え、モデルの重みは Hugging Face から取得する。

## 検証環境

| 項目 | 値 |
| --- | --- |
| ハードウェア | Apple M4 Pro、メモリ 48 GB |
| OS | macOS 27.2 |
| Python | 3.13.5 |
| PyTorch | 2.15.0 |
| 実行デバイス | MPS |
| 文字起こし | whisper.cpp v1.9.5、`ggml-large-v3-turbo.bin` |
| 音声 | macOS の `say` (Kyoko) で生成した日本語の会議風の発話。34.0 秒、16 kHz、モノラル |
| ノイズ | 白色ガウスノイズ。SNR 10、5、0、-5、-10 dB |
| 分割推論 | 5 秒のチャンク、2.5 秒のホップ |
| 全体推論 | 34 秒を 1 回で処理 |

音声には相槌と擬音を意図的に含めた。
参照文は次の通り。

```text
えーと、今日は新しい決済機能のリリースについて話します。
あー、まず、先週の障害対応ですけど、キャッシュの設定ミスが原因でした。
なるほど、それは金曜日に修正済みですね。
えー、来期の計画については、あの、まだ検討中です。
はい、では、田中さんに再発防止策のまとめをお願いします。
あー、期限は来週の金曜日でお願いします。
うん、わかりました。
じゃあ、今日は以上です。ありがとうございました。
```

## 結果

CER は、句読点、空白、話者ラベル、タイムスタンプ、相槌を除いて正規化した文字列で計算した。
値が小さいほど文字起こしが参照文に近い。
「強調なし」はノイズを加えた音声をそのまま whisper.cpp に渡した結果である。

| SNR | 強調なし | 強調あり (5 秒チャンク) | 強調あり (全体) |
| --- | ---: | ---: | ---: |
| 10 dB | 0.0000 | 0.0000 | 未計測 |
| 5 dB | 0.0000 | 0.0067 | 未計測 |
| 0 dB | 0.1200 | 0.2467 | 0.2200 |
| -5 dB | 0.2000 | 0.5000 | 0.4333 |
| -10 dB | 0.4133 | 0.9733 | 未計測 |

処理速度は 16 kHz の音声で、5 秒チャンクが実時間の約 2.4 倍の速さだった。
34 秒の音声では全体推論が実時間の約 4.3 から 4.9 倍の速さだったが、60 分の音声を 1 回で処理すると GPU メモリが足りないため、実運用では 5 秒チャンクになり、約 25 分かかる計算になる。
44.1 kHz の全体推論は音声長の約 0.7 から 1.1 倍の時間がかかった。
モデルの初回読み込みは約 14 秒、キャッシュ後の読み込みは約 0.4 秒だった。

## 結果の解釈

SNR が 5 dB 以上のときは、強調の有無にかかわらず whisper.cpp の文字起こしはほぼ正しかった。
SNR が 0 dB 以下のときは、強調すると CER が大きくなった。
強調ありの出力には、参照文にない語の置換と幻覚が増えた。
全体推論は 5 秒チャンクよりは良いが、強調なしよりは悪かった。

この結果は、RE-USE が音声の知覚品質を上げても、whisper.cpp の文字起こし精度を上げるとは限らないことを示す。
モデルカードは URGENT 2025 の評価で文字精度 (CAcc) が 81.29 から 89.17 に上がると報告している。
今回の日本語の会議風音声では、その改善を再現できなかった。

入力時と文字起こし前のどちらに入れるかという問いには、文字起こし前の方がまだ適する。
RE-USE は双方向 Mamba を使うオフラインモデルで、入力中の音声を遅延なく処理する設計ではない。
入力時に適用すると、録音中の音声が不可逆に変わり、会議の参加者が重なった発話で主話者以外が抑制される。
モデルカードも、重なった発話では主話者を保持し、他の話者を抑制すると述べている。
会議の音声は重なった発話を含むため、録音の入力時に適用するのは危険である。

## 検証の限界

- 単一話者の合成音声で検証した。複数話者、重なった発話、実会議の雑音は含まない。
- 日本語の 1 種類の音声だけで検証した。英語や多言語の会議は含まない。
- 知覚品質 (DNSMOS、PESQ、STOI) は計測していない。文字起こしの CER だけを比較した。
- whisper.cpp の large-v3-turbo だけを比較した。small や medium では結果が変わる可能性がある。
- macOS の非公式移植を使った。公式の NVIDIA GPU 実装や WebGPU 実装とは出力が異なる可能性がある。

## 再現手順

検証はアプリの依存に含めない。
次の手順は、検証用の一時環境で実行する。

```bash
git clone https://github.com/yani-/re-use-mac-unofficial /tmp/re-use-mac-port
cd /tmp/re-use-mac-port
git checkout 6d794f84097896ea0fcb36523e2fb998e23ec68d
uv venv --python 3.13 .venv
uv pip install --python .venv/bin/python -r requirements.txt

.venv/bin/python enhance.py noisy.wav -o enhanced/
whisper-cli -m ggml-large-v3-turbo.bin -f enhanced/noisy.wav -l ja -oj -of asr
```

`noisy.wav` は 16 kHz、モノラルの WAV を使う。
長い音声は `--max-full-seconds` と `--chunk-seconds` で分割方法を変える。
44.1 kHz の音声を使う場合は、強調した後に 16 kHz へ変換してから whisper.cpp に渡す。

## 再検討の条件

次のいずれかを満たしたときに、RE-USE の採用を再検討する。

- 実際の会議音声で、強調なしより CER が小さくなることを複数の会議で確認する。
- NVIDIA が Core ML または ONNX の公式な推論経路を提供する。
- 重なった発話を抑制しないモデル、または話者ごとに適用できるモデルが提供される。
- 文字起こしではなく、録音の再生品質を上げる機能として採用する。

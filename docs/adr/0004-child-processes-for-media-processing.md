# ADR-0004: エンコードと文字起こしは同梱バイナリの子プロセスに分離する

Created: 2026-10-28
Model: DeepSeek V4.1 Flash 1017
Status: Accepted

## 背景

Kataribe は、録音した音声を mp3 と 16 kHz wav に変換し、whisper.cpp で文字起こしする（PRD の R-4、T-1）。
エンコードと文字起こしは CPU を使い、60 分の会議では数分から数十分かかる。
この処理を Electron のメインプロセスや Renderer で直接実行すると、画面の応答が止まる。
アプリ全体がクラッシュすれば、処理そのものを失う。

PRD は、Electron を UI とジョブ管理に専念させ、エンコードと文字起こしを子プロセスに切り出す構成を取る。
ネイティブコードをアプリに持たせず、ffmpeg と whisper.cpp を同梱バイナリとして起動する。
処理の進捗とキャンセルを画面から扱えるようにする。

PRD の構成図には「子プロセス 4 つ」とあるが、本文で役割が確定しているのは ffmpeg と whisper.cpp である。
LLM のクライアントはメインプロセスのネットワーク処理として動かす。
4 つの内訳は未決事項とし、実装時に確定する。

## 決定

- メインプロセスにジョブ管理を置き、ffmpeg と whisper.cpp を子プロセスとして起動する。
  Renderer はジョブを直接起動せず、preload の API を経由してメインプロセスに依頼する。
- 子プロセスの起動には Node.js の `child_process.spawn` を使い、シェルを経由しない。
  引数は配列で渡し、パスはアプリの `resources` から解決する。
  会議フォルダやモデルのパスに空白や日本語が含まれても扱えるようにする。
- ffmpeg は次の 3 つの用途で起動する。
  - 録音チャンクを結合し、mp3 を作る。
  - 結合した PCM から 16 kHz、モノラルの wav を作る。
  - 再文字起こしのために、mp3 から 16 kHz、モノラルの wav を作る。
- whisper.cpp は文字起こしの実行だけに使う。
  モデルの選択、言語の指定、initial prompt、出力ファイルのパスはメインプロセスが組み立てる（ADR-0006）。
- 子プロセスの標準出力と標準エラーを読み、進捗をメインプロセスに取り込む。
  ffmpeg は `-progress pipe:1` の出力を使う。
  whisper.cpp はセグメントのタイムスタンプを含む出力を解析する。
  解析の契約は、同梱するバイナリの版ごとに固定する。
- キャンセルは、子プロセスに SIGTERM を送り、一定時間待ってから SIGKILL を送る。
  文字起こしの途中経過は、キャンセルやタイムアウトの時点で `transcript.md` に部分結果として保存する（ADR-0007）。
- 子プロセスはメインプロセスの子として起動し、`detached` にはしない。
  子プロセスを終了するのはアプリの終了時（`before-quit` と `will-quit`）と OS のログアウト時とし、メインウィンドウを隠す操作では終了しない（ADR-0012）。
  メインプロセスが強制終了した場合に備え、起動した子プロセスの PID と起動時刻を記録し、次回起動時に残存プロセスを確認して終了する。
- 子プロセスのクラッシュはアプリ全体のクラッシュにしない。
  終了コード、シグナル、標準エラーの末尾を `meta.json` とローカルのログに記録し、ジョブを `error` にする。
- エンコードと文字起こしは、MVP では同時に 1 件だけ実行する。
  複数の会議を同時に処理する機能は持たない。
- 録音中は新しい文字起こしを開始しない。
  録音を優先し、既に走っている文字起こしがある場合は、録音の開始時に一時停止するか、録音の完了後に再開する。
- 同梱バイナリは `resources/bin/<arch>/` に置き、実行権限を付ける。
  Electron の `asar` には入れず、`extraResources` で展開する。
  署名と公証の対象に含め、アプリ本体と同じ Team ID で署名する。
- ffmpeg と whisper.cpp のライセンスと著作権表示をアプリに同梱する。
  ビルドに含める外部ライブラリのライセンスも確認する。
- 子プロセスの標準出力と標準エラーは、文字起こしの本文をそのままログに残さない形で扱う。
  文字起こしの結果は `transcript.md` にだけ書き、ログには進捗、終了コード、エラーの種類だけを残す。

## 検討した選択肢

| 選択肢 | 採用しない理由 |
| --- | --- |
| Node.js の `worker_threads` でエンコードと文字起こしを動かす | ffmpeg と whisper.cpp はネイティブバイナリであり、worker_threads から直接動かせない。WASM 版は Metal と Core ML を使えず、速度も足りない可能性が高い |
| ネイティブアドオンとして組み込む | Electron の版ごとに再ビルドが必要で、アドオンのクラッシュがアプリ全体を巻き込む。署名と配布も複雑になる |
| メインプロセスで同期的に実行する | エンコード中と文字起こし中に UI が止まる。R-1 と非機能要件の応答性を満たせない |
| Renderer で ffmpeg.wasm を使う | ブラウザの WASM では Metal と Core ML が使えず、60 分の音声を 10 分で処理する目標に届かない可能性が高い |
| クラウドの文字起こし API を使う | 音声を端末外に送らないというコアバリューに反する（ADR-0013） |
| Swift のヘルパーを最初から同梱する | システム音声は BlackHole 2ch で取得するため、録音全体をネイティブヘルパーにする理由がない |
| 複数の会議を同時に文字起こしする | CPU と Metal の取り合いになり、録音中のアプリの応答性も落ちる。MVP では 1 件ずつで足りる |

## 結果

- エンコードと文字起こしがアプリの UI から分離され、処理中も画面が応答する。
  子プロセスがクラッシュしても、アプリ全体を再起動せずにジョブだけを失敗として扱える。
- 同梱するバイナリの分だけ配布物が大きくなる。
  ffmpeg と whisper.cpp のサイズを測り、PRD の 300 MB 以下という目標に収める（ADR-0014）。
- 子プロセスの起動パス、引数、環境変数、作業ディレクトリを固定する必要がある。
  ユーザーが設定した保存先やモデルのパスをそのままシェルの文字列に連結しない。
- 進捗の解析はバイナリの出力形式に依存する。
  ffmpeg と whisper.cpp の版を固定し、版を上げるときは進捗解析のテストをやり直す。
- 子プロセスの終了処理を誤ると、アプリを終了しても ffmpeg や whisper.cpp が残る。
  アプリの終了時、OS のログアウト時、次回起動時の孤児の掃除で終了処理を呼ぶ。
- ffmpeg がハングするとジョブが `encoding` のまま止まる。
  音声の長さに応じたタイムアウトを ADR-0007 で定め、SIGTERM と SIGKILL で停止する。
- 文字起こしの部分結果を残すため、子プロセスの出力を逐次読む必要がある。
  出力を最後までバッファリングすると、タイムアウト時に途中結果を失う。
- 署名と公証では、アプリ本体だけでなく `resources/bin/` のバイナリも署名する。
  hardened runtime の有効なアプリから子プロセスを起動できることを、配布ビルドで確認する。
- ffmpeg のビルドによっては GPL のライブラリが含まれる。
  配布するバイナリの構成とライセンスを確定し、必要なら LGPL の構成に差し替える。

## 未決事項

- PRD の構成図にある「子プロセス 4 つ」の内訳。
  現時点で役割が確定しているのは ffmpeg と whisper.cpp である。
- ffmpeg のビルド構成。
  libmp3lame を含む LGPL の構成にするか、GPL の構成を受け入れるか。
- whisper.cpp のビルド構成。
  Metal と Core ML をどこまで有効にし、Apple Silicon 向けのバイナリをどう配布するか。
- エンコードと文字起こしを並列に実行するか。
  mp3 の生成と 16 kHz wav の生成を同時に走らせるか、順番に走らせるか。
- 将来、複数の会議を並列に処理するか。
- 子プロセスの進捗解析の契約を、どの版の ffmpeg と whisper.cpp に対して固定するか。
- 子プロセスのログの保存場所と保持期間。
- 配布ビルドで子プロセスを起動するための hardened runtime の entitlement。

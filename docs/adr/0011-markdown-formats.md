# ADR-0011: 文字起こしと要約はプレーン Markdown の固定形式で保存する

Created: 2026-10-28
Model: DeepSeek V4.1 Flash 1017
Status: Accepted

## 背景

Kataribe の成果物は、Obsidian や Git などの既存のメモ環境にそのまま取り込めるプレーンな Markdown である（PRD の概要）。
文字起こしはタイムスタンプ付きの Markdown として保存し（PRD の T-3）、要約は「要約」「決定事項」「ToDo」「未決事項」の 4 セクションを持つ（PRD の S-4）。
文字起こしと要約はアプリ内で編集できる（PRD の T-5、S-5）。
要約は Slack や Notion にコピーして貼れること（PRD の U5）、ToDo は Obsidian でタスクとして扱えることが求められる。

文字起こしと要約の形式を固定しないと、LLM の出力のたびに見出しや項目の位置が変わり、検索と編集の処理が壊れる。
一方で、利用者が外部のエディタで自由に編集できることも、ファイルを正本にする方針（ADR-0010）の前提である。

## 決定

- 文字起こしは `transcript.md` に保存する。
  UTF-8、LF の改行、末尾に改行を 1 つ置く。
- `transcript.md` の先頭には YAML の front matter を置き、次の項目を持つ。
  - `title`: 会議のタイトル。
  - `date`: 録音の開始日時。
    ISO 8601 のタイムゾーン付き。
  - `duration`: 音声の長さ。
    `HH:MM:SS`。
  - `source`: `mic`、`system`、`mic+system` のいずれか。
  - `model`: 使用した whisper.cpp のモデル名。
  - `language`: 判定した言語のコード。
    混在する場合は `mixed`。
- LLM に送るときは、文字起こしの本文だけを送り、front matter を除く（ADR-0013）。
- front matter の後ろに空行を 1 つ置き、本文にはセグメントを 1 行ずつ書く。
  行の形式は `[HH:MM:SS] テキスト` とし、時刻はセグメントの開始時刻を秒単位で書く。
- セグメントのテキストに改行が含まれる場合は、空白に置き換えて 1 行にする。
- 要約は `summary.md` に保存する。
  UTF-8、LF の改行、末尾に改行を 1 つ置く。
- `summary.md` の先頭には YAML の front matter を置き、次の項目を持つ。
  - `title`: 会議のタイトル。
  - `date`: 会議の日付。
    `YYYY-MM-DD`。
  - `provider`: 使用した LLM のプロバイダ名。
  - `generated_at`: 要約を生成した日時。
    ISO 8601 のタイムゾーン付き。
  - `language`: 出力言語。
    `ja` または `en`。
- `summary.md` の本文は、次の 4 つの H2 セクションをこの順番で持つ。
  日本語の場合は `## 要約`、`## 決定事項`、`## ToDo`、`## 未決事項` とする。
  英語の場合は `## Summary`、`## Decisions`、`## ToDo`、`## Open Questions` とする。
- パーサーは日本語と英語の両方の見出しを認識する。
  出力言語は `language` の値と見出しの言語で判定する。
- セクションの内容が空の場合も、見出しは残す。
- ToDo の項目は `- [ ]` で始まる行とし、担当と期限を括弧書きで含める。
  日本語の場合は「担当」「期限」、英語の場合は `Owner`、`Due` を使う。
  担当と期限が不明な場合は、推測で埋めずに「担当未定」「期限未定」または `Owner TBD`、`Due TBD` と書く。
- LLM の出力に 4 つの見出しが欠けている場合は、足りない見出しを空のセクションとして補う。
  出力に余分な見出しや文章がある場合は、内容を捨てずに 4 つのセクションの後ろに残す。
- アプリ内の編集は、`transcript.md` と `summary.md` を直接書き換える。
  編集のたびに front matter を保持し、未知のキーは削除しない。
- 要約を再生成する前に、既存の `summary.md` を `summary.previous.md` に退避し、上書きの確認を出す。
- アプリは front matter を YAML として読み、タイトルに `:` や `#` が含まれる場合は引用符で囲んで書き出す。
- 文字起こしのタイムスタンプは、本文ではプレーンなテキストとして持つ。
  検索結果から音声の位置に飛ぶ機能は、この時刻を解析して実装する。
- 文字起こしの翻訳は、元の `transcript.md` を残して別の Markdown に保存する（ADR-0016）。
- HTML やアプリ独自のバイナリ形式は使わない。
  追加のメタデータは `meta.json` に置き、Markdown の本文には混ぜない。

## 検討した選択肢

| 選択肢 | 採用しない理由 |
| --- | --- |
| JSON や HTML で保存する | Obsidian や Git でそのまま読めず、コピーして Slack や Notion に貼る用途にも向かない |
| 文字起こしと要約を 1 つの Markdown にまとめる | 文字起こしが長い会議では要約が埋もれ、編集と検索の単位も曖昧になる |
| タイムスタンプを音声へのリンクにする | 再生位置に飛ぶ便利さはあるが、Markdown のリンク形式とプレイヤーの対応を決める必要がある。検索結果からのジャンプは後から実装できる |
| TOML の front matter にする | Obsidian をはじめとする Markdown のツールは YAML の front matter を標準的に扱う |
| セグメントごとに JSON の sidecar を持つ | ファイルが二重になり、外部のエディタで編集したときに同期が崩れる |
| LLM の出力をそのまま保存する | 見出しの順序や有無が出力ごとに変わり、検索と編集の処理が壊れる |
| 要約のセクションを固定しない | 利用者がテンプレートを変えられる柔軟性はあるが、MVP では 4 セクションの比較と検索を優先する |
| 文字起こしを 1 行 1 セグメントにしない | 長い段落になり、タイムスタンプと音声位置の対応が取りにくくなる |

## 結果

- 文字起こしと要約は、Obsidian、Git、テキストエディタでそのまま読める。
  行単位の差分が出るため、変更の履歴も追いやすい。
- LLM の出力が 4 セクションの形式を外す場合がある。
  見出しを補い、余分な内容を残すことで、利用者の待ち時間を無駄にしない。
- 文字起こしの行を外部のエディタで編集すると、タイムスタンプと本文の対応が崩れる可能性がある。
  アプリは行の形式を検査し、解析できない行はそのまま残して警告を出す。
- タイトルに YAML の予約文字が含まれる場合、front matter の書き出しで引用が必要になる。
  YAML のシリアライザーを使い、手で文字列を連結しない。
- 文字起こしの時刻は秒単位なので、同じ秒に複数のセグメントがある場合は順序だけが手がかりになる。
  開始時刻と終了時刻の両方を持つかは、検索と再生の精度を見て決める。
- ToDo のチェックボックスは Obsidian のタスクとして扱える。
  担当と期限の表記を固定することで、後から集計しやすくなる。
- 翻訳は `transcript.<lang>.md` に保存するため、原文との対応を保つ方法が必要になる（ADR-0016）。
- 検索の索引は、この形式を解析して作る（ADR-0010）。
  形式を変えるときは、索引の再構築が必要になる。

## 未決事項

- 日本語と英語以外の出力言語を追加するときの見出しと ToDo の表記。
- 検索結果から音声の位置に飛ぶときのリンク形式。
- セグメントのテキストに `[` や改行が含まれる場合のエスケープ規則。
- front matter に `schema_version` と `edited_at` を追加するか。
- `summary.md` の front matter に `model` を追加するか。
- LLM の出力が 4 セクションから大きく外れた場合に、どこまで自動で補正するか。
- `summary.md` に利用者が独自のセクションを追加できるようにするか。
- タイムスタンプを開始時刻だけにするか、終了時刻も持つか。
- 話者分離を入れるときの話者名の表記。
- LLM の生の応答を、監査や再生成のために別ファイルに残すか。

# ADR-0016: 文字起こしの翻訳は元のファイルを残して別の Markdown に保存する

Created: 2026-10-28
Model: DeepSeek V4.1 Flash 1017
Status: Accepted

## 背景

Kataribe は、多言語が混在する会議の文字起こしを、話された言語のまま残す（PRD の T-7）。
そのうえで、文字起こしの日本語訳または英語訳を、LLM によるオプションとして提供する（PRD の T-7）。
翻訳は Must の要件であり、会議詳細から利用者が明示的に実行する操作になる。
翻訳を実行すると、文字起こしのテキストが LLM に送られるため、要約と同じく送信前の確認が必要になる（PRD の S-3）。

原文を上書きすると、話された言語の記録が失われる。
要約の 4 セクションに翻訳を混ぜると、要約と文字起こしの境界が曖昧になり、検索の単位も崩れる。
原文と翻訳を別のファイルに分け、原文を正本として残す必要がある。

## 決定

- 翻訳は、会議詳細の文字起こしタブから利用者が明示的に実行する。
  対象言語は日本語と英語とし、原文の言語と同じ場合は操作を無効にする。
- 翻訳に送るのは `transcript.md` の本文だけとする。
  front matter のタイトル、日付、長さ、モデル名は送らない（ADR-0013）。
- 送信の前に、ADR-0008 と ADR-0013 と同じ確認ダイアログを出す。
  プロバイダ名、モデル名、エンドポイントの完全な URL、送る本文のプレビュー、文字数、内容のハッシュ、概算のトークン数と料金を表示する。
- 翻訳の結果は、対象言語のコードを使って `transcript.ja.md` または `transcript.en.md` に保存する。
  元の `transcript.md` は変更しない。
- 翻訳ファイルの front matter は、`title`、`date`、`duration`、`source`、`model`、`language`、`source_language`、`provider`、`generated_at` を持つ。
  `language` は翻訳先の言語、`source_language` は原文の言語または `mixed` とする。
- 翻訳ファイルの本文は、元の `transcript.md` と同じ `[HH:MM:SS] テキスト` の形式にする。
  セグメントの開始時刻は変えない。
  セグメントの数が原文と一致しない場合は、翻訳を部分結果として保存し、一致しない旨を画面に出す。
- 翻訳のプロンプトでは、タイムスタンプを保持し、セグメントを結合または分割しないよう指示する。
  話者、固有名詞、数値、日付は、推測で補わず、原文の表現を尊重する。
- 翻訳を再実行するときは、既存の翻訳ファイルを `transcript.<lang>.previous.md` に退避し、上書きの確認を出す。
- 要約の生成には、翻訳ではなく元の `transcript.md` を使う。
  翻訳を要約に使う機能は MVP では持たない。
- 検索の索引には、翻訳ファイルの本文も言語の属性付きで含める。
  全文検索の UI は次フェーズで実装する（PRD の F-5）。
- 翻訳の失敗時は、元の `transcript.md` と既存の翻訳ファイルを変更しない。
  エラーを表示し、再実行の操作を残す。
- 翻訳は自動では実行しない。
  録音、文字起こし、要約の完了時に、翻訳リクエストを送ることもない。
- 翻訳に使う LLM のプロバイダとモデルは、要約と同じ設定を使う。
  会議ごとに別のプロバイダを選ぶ機能は MVP では持たない。

## 検討した選択肢

| 選択肢 | 採用しない理由 |
| --- | --- |
| 元の `transcript.md` を翻訳で上書きする | 話された言語の記録が失われ、原文と翻訳を比較できなくなる。T-7 の「話された言語のまま残す」に反する |
| `summary.md` に翻訳のセクションを追加する | 要約と文字起こしの境界が曖昧になり、検索と編集の単位が崩れる。要約の 4 セクションの形式も崩れる |
| 翻訳を JSON の sidecar に保存する | Obsidian や Git でそのまま読めず、プレーンな Markdown というコアバリューに反する |
| 音声を LLM に送って翻訳する | 音声を端末外に送らない方針に反する（ADR-0013） |
| ローカルの翻訳モデルを使う | モデルのサイズと品質の両立が難しく、MVP の範囲を超える。将来の選択肢として残す |
| 翻訳を自動で実行する | 文字起こしを LLM に送る判断を利用者から奪う。S-3 に反する |
| 翻訳のセグメントを結合して 1 つの文章にする | 音声の位置との対応が失われ、検索結果から再生位置に飛べなくなる |

## 結果

- 原文と翻訳が別のファイルになるため、話された言語の記録を残したまま、日本語と英語の両方を読める。
  会議フォルダのファイルが増えるが、ファイル名で用途が分かる。
- 翻訳ファイルにもタイムスタンプを残すため、検索結果から音声の位置に飛べる。
  ただし、翻訳のセグメント数が原文と一致しない場合は、位置の対応が崩れる。
- 翻訳の実行には、文字起こしの送信と同じ確認と課金が発生する。
  長い会議では、翻訳のトークン数と料金が要約より大きくなる可能性がある。
- 翻訳の品質は、プロバイダとモデルに依存する。
  固有名詞、数値、日付の誤りは、利用者が原文と比較して修正する必要がある。
- 翻訳ファイルを検索の索引に含めることで、日本語でも英語でも同じ会議を探せる。
  索引の言語属性とランキングは、全文検索の実装時に決める。
- 要約が原文を使うため、翻訳を実行しても要約の内容は変わらない。
  翻訳を要約に使いたい場合は、別の操作として設計する必要がある。
- 翻訳の再実行で既存の翻訳を上書きする場合は、退避ファイルと確認が必要になる。
  会議フォルダのファイルが増えるため、退避ファイルの保持期間を決める必要がある。

## 未決事項

- 将来、翻訳を要約に使う機能を入れるか。
- 日本語と英語以外の翻訳先を追加するか。
- 翻訳のセグメント数が原文と一致しない場合に、自動で対応付けるか、利用者に修正させるか。
- 翻訳ファイルを全文検索の索引に含めるときの言語属性とランキング。
- 退避ファイル `transcript.<lang>.previous.md` の保持期間と削除の方法。
- 翻訳の品質を測る指標と、プロンプトの調整方法。
- 会議ごとに翻訳のプロバイダを変える機能を入れるか。
- 翻訳を実行した事実を `meta.json` に記録するか。

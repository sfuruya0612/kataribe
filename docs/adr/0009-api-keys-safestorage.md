# ADR-0009: API キーは Electron の safeStorage で macOS Keychain に保存する

Created: 2026-10-28
Model: DeepSeek V4.1 Flash 1017
Status: Accepted

## 背景

Kataribe は、複数の LLM プロバイダの API キーを設定画面で登録する（PRD の S-1、S-8）。
API キーは macOS の Keychain に保存し、ログやファイルに平文で残さない（PRD の S-2）。
API キーが漏れると、利用者の課金とレート制限に直接影響する。
会議の文字起こしは機密情報を含むため、設定ファイルの漏洩とログの漏洩を別々に防ぐ必要がある。

Electron の `safeStorage` は、macOS では Keychain を裏付けにした暗号化を提供する。
API キー自体を Keychain の項目として保存するのではなく、Keychain で保護された鍵で暗号化した文字列を設定ファイルに置く。
追加のネイティブモジュールを入れずに、文字列の暗号化と復号ができる。
暗号化された文字列はアプリの設定ファイルに保存し、復号はメインプロセスだけで行う。

## 決定

- API キーは Electron の `safeStorage.encryptStringAsync` で暗号化し、Base64 に変換して設定ファイルに保存する。
  復号には `safeStorage.decryptStringAsync` を使う。
  同期 API の `isEncryptionAvailable`、`encryptString`、`decryptString` は Electron 46 で削除されるため使わない。
  非同期 API が利用できる Electron の版を最低要件とし、ADR-0001 と ADR-0003 の動作確認で固定する。
  42 以降を目安とする。
  設定ファイルに平文の API キーを書かない。
- API キーの復号はメインプロセスだけで行う。
  Renderer には API キーを渡さない。
  設定画面にはマスクした表示だけを出し、新しいキーを入力したときはメインプロセスに送って暗号化する。
- `safeStorage.isAsyncEncryptionAvailable()` が false の場合は、平文にフォールバックせず、API キーの保存と LLM の送信を無効にする。
  画面には、macOS の Keychain が利用できないため設定を保存できない旨を出す。
- `decryptStringAsync` が一時的に利用できないエラーを返した場合は、Keychain のロック解除後に再試行する。
  `shouldReEncrypt` が true の場合は、復号したキーを新しい鍵で再暗号化して保存する。
- 設定ファイルは `~/Library/Application Support/Kataribe/config.json` に置き、ファイルの権限を 0600 にする。
  設定ファイルには、LLM プロファイル ID、プロバイダ、エンドポイント URL、モデル名、暗号化した API キーを保存する。
- API キーは LLM プロファイル ID ごとに 1 つ保存する。
  同じプロバイダでも ID を分ければ、複数のアカウントや組織を登録できる。
- API キーは LLM プロファイル ID と、キーを入力したときのエンドポイントのホストに束縛する。
  設定画面でホストを変更したら、保存済みのキーを再利用せず、再入力を求める。
- カスタムヘッダーで `Host`、`Authorization`、`Cookie` を上書きできないようにする。
  リダイレクトを追う場合は、別のホストに認証ヘッダーを送らない。
- API キーの変更と削除の操作を設定画面に用意する。
  削除したキーは設定ファイルから消す。
  バックアップに残った暗号文は復号できる可能性があるため、削除後はプロバイダ側でキーを無効化するよう案内する。
- API キーをログ、標準出力、標準エラー、クラッシュレポート、エラーメッセージに含めない。
  リクエストのヘッダーをログに出す場合は、`Authorization`、`x-api-key`、`api-key`、`x-goog-api-key` と、URL のクエリ文字列の秘密を固定の文字列に置き換える。
  ログに会議フォルダのパスを出す場合は、タイトルをハッシュ化するか、パスを出さない。
- API キーを含む設定の読み込みに失敗した場合は、キーが無効である旨を画面に出し、再入力を求める。
  Keychain がロックされている場合は、macOS のログイン後に再試行するよう案内する。
- 設定ファイルを別の Mac にコピーしても、Keychain を移行していない限り API キーは復号できない。
  別の Mac では API キーを再入力する必要があることを、設定画面の注意書きに含める。
- 開発中に環境変数で API キーを差し込む場合は、本番の設定ファイルに保存しない。
  開発用の経路は、リリースビルドでは無効にする。
- 設定ファイルのバックアップと移行のために、暗号化されたキーの形式にバージョンを付ける。
  形式を変えるときは、古い形式を読める移行処理を用意する。

## 検討した選択肢

| 選択肢 | 採用しない理由 |
| --- | --- |
| keytar などの Keychain ライブラリ | ネイティブモジュールのビルドと Electron の版への追従が必要になる。safeStorage は Electron に含まれている |
| 設定ファイルに平文で保存する | PRD の S-2 に反する。設定ファイルのバックアップや共有からキーが漏れる |
| 環境変数だけで運用する | GUI アプリの利用者には設定しにくく、シェルの履歴やプロセスの環境から漏れる可能性がある |
| macOS の `security` コマンドを呼ぶ | キーチェーンの操作にシェルを経由することになり、プロンプトとエラーの扱いが不安定になる |
| 1Password CLI などの外部ツールに預ける | 外部ツールのインストールと認証が前提になり、アプリ単体で完結しない |
| アプリ独自の鍵で暗号化する | その鍵をどこに保存するかという問題が残る。OS の Keychain に預けるほうが安全である |
| API キーを Renderer に渡して保存する | Renderer の不具合や XSS でキーが読まれる。復号と利用はメインプロセスに閉じる |

## 結果

- API キーは macOS の Keychain に守られ、設定ファイルには暗号文だけが残る。
  Keychain のロック状態やユーザーのログイン状態によって、復号に失敗する場合がある。
- `safeStorage` は Electron の API なので、Electron の版を上げるときに暗号化の互換性を確認する必要がある。
  非同期 API は Keychain のユーザー入力待ちでメインスレッドを止めないが、Keychain のロックや拒否で失敗する場合がある。
  既存の暗号文が読めなくなると、利用者はキーを再入力することになる。
- 設定ファイルを別の Mac にコピーしても、通常は API キーを復号できない。
  ただし、ログイン Keychain を Migration Assistant や Time Machine で移行した場合は復号できる可能性がある。
  会議データのフォルダはコピーで移せるが、API キーは移せないことを基本として明示する。
- API キーを Renderer に渡さないため、設定画面の表示と更新の API を preload で設計する必要がある。
  入力中の値は Renderer のメモリに一時的に存在するが、保存後は表示しない。
- ログの redaction をテストで確認する。
  API キーらしい文字列を含むリクエストを流し、設定ファイル、ログ、標準出力のどこにも平文が残らないことを検証する。
- 開発用の環境変数の経路を残すと、リリースビルドで誤って有効になる可能性がある。
  ビルドのフラグで無効化し、テストで確認する。
- キーの削除後にプロバイダの設定が残ると、送信時に認証エラーになる。
  削除の操作では、プロバイダの設定を残すか消すかを利用者に確認する。

## 未決事項

- 設定ファイルの schema と、暗号化されたキーの格納形式のバージョン。
- bundle identifier と Team ID を変更した場合の、Keychain の再許可とキー再入力の移行手順。
- GitHub の PAT のように、API キー以外の資格情報を同じ仕組みで扱うか。
- キーのローテーションを促す条件と、期限切れの通知。
- Keychain のロックが解除されたことを検知して、自動で再試行するか。
- 開発用の環境変数による上書きを、どのビルドで許可するか。
- 設定ファイルのバックアップと復元の手順。

# ADR-0025: 要約の前に相槌と擬音を LLM で除去し、除去に失敗したときは元の文字起こしで要約する

- Status: Accepted

## Context

会議の文字起こしには「あー」「えーと」「なるほど」「うん」などの相槌と、「（笑）」「あはは」などの擬音が含まれる。
要約は文字起こしの本文を LLM に送って生成するため、相槌と擬音が多い会議では、要約、決定事項、ToDo の密度が下がる(PRD の `REQ-SUMMARY-002`)。

相槌と擬音を機械的に判定する方法は、文脈によって意味を持つ「なるほど」「はい」を落とす危険がある。
利用者から、要約の前に LLM に文字起こしを整えさせ、その結果から要約を作りたいという要求がある。

文字起こしはタイムスタンプと話者ラベルを持つ(ADR-0011)。
整えた本文がタイムスタンプや話者ラベルを失うと、会議詳細の表示と音声位置への移動が壊れる。
整える処理は同じ LLM プロファイルを使うため、送信回数とトークン数が増える。
送信の確認は要約の生成時に 1 回行う(ADR-0008)。

## Decision

- 設定に `removeFillersBeforeSummary` を追加し、既定を有効にする。
- 要約の生成時にこの設定が有効なら、要約の前に、同じ LLM プロファイルと送信先で文字起こしを整える。
- 整える処理のシステムプロンプトは、相槌と擬音だけを削除し、発話の内容、話者ラベル、タイムスタンプ、行の順序を変えないよう指示する。
  相槌だけの発話行は削除してよい。
  出力は整えた文字起こしだけとし、要約、言い換え、見出しの追加を禁止する。
- 整える処理は 8,000 文字以下の行単位の区間に分割する。
  各区間の出力は、入力に存在するタイムスタンプと話者ラベルを順序を保って含み、本文が入力の文字の削除だけで得られることを検査する。
  検査に失敗した区間は元の本文を使い、失敗した区間があることを記録する。
- すべての区間で整える処理に失敗したときは、元の文字起こしで要約を生成する。
  要約の生成自体は失敗させない。
- 整えた本文はファイルとして保存しない。
  要約に使った本文の文字数、除去した文字数、区間数、失敗した区間数を `meta.json` の `summary.cleanup` に記録する。
- 送信前の確認ダイアログに、整える処理でも文字起こしを送ること、送信が 2 回になること、概算トークン数が増えることを表示する。
- 要約の出力言語は、整える設定で変更しない。
  整える処理は入力の言語を保つ。
- 会議タイトルの生成には、整えた本文を使う。
- タイトル生成に失敗しても要約は成功させ、失敗理由を `meta.json` の `title_generation` に記録する。
  会議詳細に理由と再試行を表示する。

## Consequences

- 相槌と擬音が多い会議では、要約と ToDo の密度が上がる。
  一方で、文脈を持つ「なるほど」「はい」まで削除する可能性がある。
- LLM の呼び出しが 1 回増えるため、待ち時間と料金が増える。
  確認ダイアログに送信回数を表示し、設定で無効にできるようにする。
- 整える処理の出力がタイムスタンプを失った場合は、元の本文に戻す。
  部分的に失敗した区間が混ざるため、要約に使った本文は会議ごとに一定にならない。
- 整えた本文を保存しないため、要約の根拠を後から一字一句確認できない。
  必要になった場合は、除去した本文を別ファイルに保存する判断を別途行う。
- プロンプトインジェクションの危険は、要約と同じく残る。
  整える処理でも文字起こしをデータとして扱い、その中の指示に従わないよう指示する。
